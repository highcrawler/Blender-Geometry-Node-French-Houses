# Phase 9C — future roof architecture (analysis only)

The current roof assumes **one axis-aligned rectangular Cottage**, a single straight ridge parallel to depth (Y), two continuous equal-length pitched faces, one global pitch and wall height, symmetric overhangs, and one gable at each Y endpoint. It obtains the ridge from width/pitch, deck length from depth, then lays independent shingle rows along each face. `roof_geometry` uses a module-global Cottage `p` and the scene collection, and directly creates its four roof materials; these are coupling points, not yet a freestanding API. The existing shingle placement, deterministically seeded width/row logic, deck mesh and per-side ridge caps might later be isolated into rectangular roof-surface operations, but **no such refactoring is done in Phase 9C**. Its reported-course inconsistency must first be addressed and retested against both archived reference meshes.

An L-shaped building would need at least two explicitly specified roof volumes and a defined joining strategy: intersection lines between planes, a valley (Dachkehle) with water-shedding/flashing geometry, clipped shingle courses terminating at the valley, and a solution for overlapping or unequal-height ridges/eaves. U-shaped layouts introduce multiple valleys and water collection; side annexes and varying wing heights introduce T-junctions and step flashing. Independent rectangular roofs cannot simply overlap as finished assets: hidden surfaces, inverted or exposed end cuts, intersecting caps, ambiguous course continuity and drainage paths need a coordinated roof-topology model and robust polygon clipping/trim rules. These are later architecture decisions, **not** proven by this rectangular test. No L-/U-model, roof-intersection engine or new roof feature was implemented here.
